# Task 01 handoff — toolchain and Rust ELF spike

## Status

**DONE.** Static, container, reproducibility, ABI, size, symbol, relocation,

## Summary and decisions

- Added a Cargo workspace containing only the manual `pass-through` fixture.
  Both Smooth Echo directories are explicitly excluded until framework crates
  exist.
- Pinned Rust 1.85.1 and `thumbv7em-none-eabihf`.
- Derived from the SDK image by immutable digest and installed checksum-pinned
  Rust distribution archives rather than a moving rustup bootstrap.
- The SDK README's claimed GCC 10.3 does not match the image. Actual tools are
  GCC 9.2.1 (2019-q4) and binutils 2.34.
- The fixture duplicates only the minimum packed ABI for this spike. Compile-time
  assertions fix parameter/header sizes (32/8/376 bytes) and 32-bit runtime
  descriptor sizes (16-byte hooks, 32-byte descriptor).
- Rust is compiled as a PIC static archive with Cortex-M7, size optimization,
  one codegen unit, fat LTO, panic abort, and remapped source paths. GNU GCC then
  final-links it with the checked-in SDK `unit.ld`. Every required symbol is an
  explicit archive root before section GC.
- Hardware testing discovered that LLVM's default MergeFunctions optimization
  aliases identical exported callbacks to one address, which the NTS-3 silently
  rejects. The pinned build uses `-mergefunc-use-aliases=0`; inspection fails if
  any required callbacks alias or lack the Thumb bit.
- No ELF patch is applied. GNU linking naturally emits System V OSABI, ET_DYN,
  EABI5, hard-float, and Thumb-2 output.
- The Rust artifact has no undefined dynamic symbol and no relocations. The SDK
  script creates a zero-sized `.rel.plt`, but Rust has no `.plt`; consequently no
  ARM-mode PLT is reachable and `--long-plt` is neither needed nor added. The C
  dummy baseline has two `R_ARM_JUMP_SLOT` entries and a non-empty PLT.
- LLVM identifies Cortex-M7 output as FPv5/FP-D16; GCC's conservative SDK output
  identifies VFPv4-D16. Both are v7E-M Thumb-2 hard-float, and STM32H725/Cortex-M7
  supports FPv5. The pass-through disassembly contains no FP instruction. This
  difference remains a hardware-validation observation, not a patched flag.

## Hardware pass-through gate

Load the exact hash above and record device firmware plus results for:

- install/select and clean stereo pass-through;
- bypass/select and suspend/resume repeatedly;
- same unit loaded in all four runtimes;
- power-cycle and reload saved program;
- unload/reload.

Hardware setup reported by the user: NTS-3 firmware displays `1.1.x`, Windows
recognizes its MIDI endpoints, KORG KONTROL EDITOR 2.5.1 is installed, computer
stereo output is connected to NTS-3 input, and headphones monitor NTS-3 output.

First Rust hardware attempt — **FAIL**: importing the Rust unit into the editor
and pressing SEND showed no error but did not persist it; RECEIVE cleared the
row. The editor console fully parsed its ELF/header and reported `Read Unit File
: OK`; the failure therefore occurs during or after device-side loading.

The source-built official C control at
`target/nts3/pass-through/c-control/c_pass_through.nts3unit` (SHA-256
`bd8cdf74c454bf1bc16347b8a234c18ab3560ca3dcdb7d487053c0299f5ac358`)
**loads, persists, and passes audio correctly**, proving the editor, transfer,
firmware, and audio setup work. Switching into the C pass-through sometimes
produces a small transient pop even from another pass-through; steady audio is
correct, so this is recorded as a runtime switching observation.

The first Rust header declared zero parameters, and the console consequently
showed no parameter parsing while the accepted C control showed four. A second
reproducible Rust diagnostic now declares one valid no-op parameter while
retaining the same DSP/ELF structure. Its SHA-256 is
`28e418d4f091dd8fe5f3aa2f9b7334331d286717232c3bea4229903a83234fea`;
hardware result: **FAIL**, so zero parameters are ruled out.

A second isolated diagnostic discards only Rust's unusable `.ARM.exidx*` and
`.ARM.extab*` sections through an additive linker script while continuing to
use the unmodified SDK `unit.ld`. This restores a dedicated `.unit_header`
PT_LOAD (file/memory size `0x178`, containing only `.unit_header`) instead of
the rejected artifact's `0x180` segment containing an extra unwind index.
Artifact: `target/nts3/pass-through/rust_pass_through_no_unwind.nts3unit`,
SHA-256 `7f4583a7e74f130718f5e2e45df020035db1a3fa4ebd09c820ed014a142dac54`;
hardware result: **FAIL**, so unwind placement is ruled out as the sole cause.

The next diagnostic keeps the dedicated header segment but changes only
`unit_init` to an unconditional two-instruction success return (`movs r0,#0`;
`bx lr`). This distinguishes descriptor validation from failure before callback
execution. Artifact:
`target/nts3/pass-through/rust_pass_through_unchecked_init.nts3unit`, SHA-256
`caaa41a1fc622aa2630fb4a33d2977ee6998dd96ca5b895a18d533ccacc848a7`;
hardware result: **FAIL**, ruling out descriptor validation and showing that
failure occurs before or independently of `unit_init`.

The next isolated diagnostic adds a no-op `.init_array` entry and its single
`R_ARM_RELATIVE` relocation, matching metadata present in known working SDK and
third-party Rust units. It retains unconditional `unit_init` and the dedicated
header segment. Artifact:
`target/nts3/pass-through/rust_pass_through_init_array.nts3unit`, SHA-256
`6928e4ebdacca0017e185cf9685ee8f1a202f75a5fb8cec68bbb1d71b54b6b98`;
hardware result: **FAIL**, so init-array/REL metadata alone is insufficient.

All known working SDK and prior Rust outputs also contain the SDK weak fallback
header after the strong unit header, making `.unit_header` and its dedicated
PT_LOAD exactly `0x2f0` bytes on NTS-3. The next diagnostic links the unmodified
SDK `_unit_base.c` object after Rust, retaining strong Rust callbacks/header but
reproducing that two-header segment. It otherwise retains the failed init-array
variant. Artifact:
`target/nts3/pass-through/rust_pass_through_sdk_fallback.nts3unit`, SHA-256
`4cbdc2928f80afd60fb9d593f61a8f98a95a62c9b304cdbed4298f8e67eb6474`;
hardware result: **FAIL**, ruling out the duplicate fallback header.

The next isolated diagnostic adds an unused C probe that forces one local
`R_ARM_JUMP_SLOT`, `.plt`, and PLTGOT entry; no SDK callback reaches this probe.
The link uses GNU `--long-plt`, and retains the preceding fallback/init/header
baseline. This tests whether firmware requires PLTGOT setup despite the pure
Rust unit having no legitimate external call. Artifact:
`target/nts3/pass-through/rust_pass_through_plt.nts3unit`, SHA-256
`808d884afcc93a3f1caa1ff490ed61bd805e63d1d72db427556ca706af2b6801`;
hardware result: **FAIL**, ruling out PLTGOT/GOT/JMPREL structure.

The next isolation removes all remaining header-semantic uncertainty: Rust's
header is omitted and the exact source-built, known-working C control header
(IDs, name, four descriptors and mappings) is linked first, followed by the SDK
fallback header. Rust still supplies all selected callbacks and DSP; prior
init/PLT metadata remains. Artifact:
`target/nts3/pass-through/rust_pass_through_c_header.nts3unit`, SHA-256
`bee650f30745aa801149b58a9162d1c53d80dfc4da332c24af29fe54386d8499`;
hardware result: **FAIL**, ruling out header contents and mappings.

LLVM had merged several semantically identical empty callbacks to the same
Thumb address, unlike GCC's working output. The next diagnostic gives every
required callback a distinct address using different counts of side-effect-free
NOP instructions, while retaining the exact working C header and prior dynamic
metadata. Artifact:
`target/nts3/pass-through/rust_pass_through_distinct_callbacks.nts3unit`,
SHA-256 `5c3b931f6c1d7d666b679095d58b4a065bd86e00cf90dba80e4b55786f84917e`;
hardware result: **PASS**. This differs from the immediately preceding failed
artifact only by unique callback addresses, proving LLVM's alias-based identical
function merging is rejected by the NTS-3 loader.

A clean minimal confirmation uses LLVM's pinned
`-mergefunc-use-aliases=0` option instead of NOPs. LLVM may still fold identical
implementations but emits each export at a distinct address. It removes all
other diagnostics: Rust header, validated `unit_init`, no fallback C header, no
init array, no PLT, and the original SDK linker behavior. Artifact:
`target/nts3/pass-through/rust_pass_through_merge_thunks.nts3unit`, SHA-256
`8f2f70bcc64d54b394692eede58573fc3620032fff935ccd5ec44d26fdeae5a6`;
hardware result: **PASS**. It loads as `Rust Pass Through`, passes left/right
stereo correctly, switches from another effect and bypasses repeatedly without
the C control's observed pop, runs in all four effect runtimes simultaneously,
persists after NTS-3 restart, and persists in a saved program containing only
this unit. Clear/SEND/RECEIVE removes it, and reinstall/SEND/RECEIVE restores it
with correct audio. The cleaned canonical `pass_through.nts3unit` rebuild is
byte-identical to this hardware-tested artifact.

Loader and lifecycle acceptance are verified for this hash on firmware reported
as `1.1.x`. Worst-case stack/CPU headroom remains unmeasured; the accepted device
also resolves the FP-attribute concern for this pass-through code path.
